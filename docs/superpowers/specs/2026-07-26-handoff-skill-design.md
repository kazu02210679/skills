# Codex向けHandoff Skill設計

## 目的

長期化・劣化した会話を、意図や判断経緯を失わずに新しいタスクへ移す `handoff` Skillを作る。
Codexでは利用可能なタスク管理機能を使って引き継ぎ先を直接作成し、ChatGPTなど同等の機能が
ない環境では、完全な引き継ぎ文書を返す。

参考元はtegnikeの
[Codex Session Handoff Skill](https://gist.github.com/tegnike/09dbb98711d8b91e66de21611f5b88ff)
とする。参考元のMITライセンスと出典をリポジトリへ保存する。

## 成功条件

- 「引き継いで」「別タスクへ移して」などの明示的な依頼で起動する。
- 次のタスクが、目的、現在地、決定事項、未解決事項、次の一手を復元できる。
- Codexのタスク作成機能が利用可能なら、新しいタスクを直接作成して全文を渡す。
- タスク作成機能が利用できない場合も、コピー可能な引き継ぎ文書を失わない。
- 元のタスク、Gitブランチ、ワークツリーを引き継ぎのためだけに変更しない。
- 秘密情報、不要な個人情報、内部思考を引き継ぎへ含めない。
- CodexとChatGPTで同じ `SKILL.md` を利用できる。

## 採用方式

### Codex優先・適応型

一つのSkill内で、利用可能な機能に応じて実行経路を選ぶ。

1. Codexのタスク管理機能がある場合は、新しいタスクを直接作成する。
2. ファイル出力はできるがタスク作成ができない場合は、一時Markdownと全文を返す。
3. どちらも利用できない場合は、会話内にコピー可能な全文を返す。

文書生成専用方式は、Codexで手動操作が増えるため採用しない。製品別Skill方式は、指示が分岐して
改善内容がずれるため採用しない。

## Skill構成

```text
skills/handoff/
├── SKILL.md
└── agents/
    └── openai.yaml

third_party/handoff-gist/
├── LICENSE
└── source.json
```

補助スクリプトは作らない。タスク管理ツール名や保存先は実行環境ごとに異なるため、固定スクリプト
よりもSkill内の分岐指示が適している。

## 起動条件

次の意図をfrontmatterの `description` に含める。

- 会話や作業を新しいタスク・スレッド・セッションへ移す。
- 長くなった、遅くなった、混乱した会話を新しくする。
- 現在の文脈を保って別タスクで続ける。
- 「引き継いで」「別セッションに移して」「新しいタスクにして」などの自然言語。

「会話が長い」と述べただけで移動を依頼していない場合は、実行せず提案に留める。

## 引き継ぎデータモデル

引き継ぎ文書は次の順序を基本とする。該当情報がない節は省略できる。

1. `Why this task exists`
   - 最初の必要性、ユーザーが得たい結果。
2. `Current objective`
   - 現在の焦点と完了条件。
3. `Trajectory and decisions`
   - メッセージ列ではなく、転換点、修正、意思決定単位で記録する。
4. `Current state`
   - 完了済み、進行中、未着手を区別する。
5. `Friction and failed approaches`
   - 障害、失敗、再試行すべきでない方法、そこから得た発見。
6. `Constraints and preferences`
   - ユーザーが明示した制約と好み。推測は推測と表示する。
7. `Open questions and next actions`
   - 未解決事項と、最初に行う一つの具体的な行動。
8. `Relevant artifacts`
   - ファイル、PR、コミット、Issue、URLと必要な理由。
9. `Suggested skills`
   - 次のタスクで明確に有用なSkillだけを挙げる。
10. `First response contract`
    - 新しいタスクは目的、現在地、未解決事項、次の行動を復唱し、ユーザーの確認を待つ。

各記述は、事実、推測、不明点を混同しない。コード差分、ログ、仕様書など、ワークスペースから
復元できる情報は複製せず参照する。

## 実行フロー

### 1. 範囲を決める

ユーザーの明示的な引き継ぎ依頼と現在の会話から対象を推定する。欠けた選択によって引き継ぎ先や
対象作業が変わる場合だけ質問する。

### 2. 履歴を回収する

現在見えている会話を起点にする。会話が要約・圧縮され、目的や主要な転換点が不明な場合に限り、
タスク読み取り機能を探して必要な範囲を遡る。ワークスペースや実行中プロセスは、作業状態の主張を
確認する必要があるときだけ読む。

### 3. 引き継ぎ文書を作る

引き継ぎデータモデルに沿って、元の会話と同じ言語で作成する。冗長な挨拶、承認だけの応答、生ログ、
一般的なリポジトリ説明は省く。

### 4. 安全性を確認する

トークン、Cookie、APIキー、パスワード、秘密鍵、不要な個人情報を削除する。観測可能な行動と
明示された理由だけを記録し、内部思考やchain-of-thoughtを含めない。

### 5. 一時バックアップを保存する

ファイル書き込みが可能なら、OSの一時ディレクトリへ一意なMarkdown名で保存する。リポジトリ内には
保存しない。失敗しても引き継ぎ全文を失わず、次の経路へ進む。

### 6. 新しいタスクを作る

タスク管理機能を検索する。利用可能なら、forkではなく新しいタスクを作成し、初期プロンプトへ
引き継ぎ全文を直接含める。

- 元と同じプロジェクトを優先する。
- 元の作業場所をそのまま利用できる環境を選ぶ。
- 引き継ぎだけのためにブランチやワークツリーを作らない。
- タイトル管理があれば、継続内容を示す短いタイトルを付ける。
- 新しいタスクには理解内容の復唱だけを要求し、ツール利用や作業開始を禁止する。

作成後は成功を確認する。作成できない場合は、作成したと報告せず、バックアップ先とコピー可能な
全文を返す。

### 7. 元のタスクを閉じる

作成したタスクとバックアップ先を短く報告する。全文の直接送信に成功した場合、元のタスクで全文を
繰り返さない。元のタスクは削除、アーカイブ、圧縮しない。

## ChatGPTでの動作

ChatGPT Skillsとしてインストールされた場合も同じ文書生成規則を使う。Codexタスク作成機能が
公開されていなければ、Markdownまたは会話内の全文を返す。ChatGPTの新しいチャットを作成したと
偽ってはならない。

ChatGPTとCodexではSkillが自動同期されないため、利用者が各製品へ個別にインストールする。

## エラー処理

| 状況 | 動作 |
|---|---|
| 履歴の一部が見えない | 不確実な点を明示し、事実として補完しない |
| 一時ファイルへ保存できない | 全文を会話内で保持して続行する |
| タスク管理機能がない | コピー可能な全文と新規タスク開始手順を返す |
| 新規タスク作成に失敗した | 失敗を明示し、バックアップ経路へ移る |
| 引き継ぎ先の確認応答がない | 作成成功と理解確認を区別して報告する |
| 秘密情報の可能性がある | 値を削除し、必要なら秘密情報が存在した事実だけを記録する |

## 検証

### 形式検証

- `python scripts/validate-skills.py`
- Codex `skill-creator/scripts/quick_validate.py`
- `agents/openai.yaml` のYAML読み込み
- UTF-8読み込み

### フォワードテスト

少なくとも次の3ケースを独立したエージェントで試す。

1. 長い実装作業の途中で明示的に新しいタスクへ移す。
2. タスク作成機能がない環境でMarkdownへフォールバックする。
3. 会話に秘密情報の例、失敗した方法、ユーザーの方針変更が含まれる。

確認項目：

- 元の目的と現在の目的を区別できる。
- 失敗やユーザー修正を落とさない。
- 秘密値を出力しない。
- 新しいタスクが作業を始めず理解確認で止まる。
- 利用不能な機能を実行したと偽らない。

フォワードテストでは、Skillへ期待解や設計意図を渡さず、実際の利用に近い依頼と会話だけを渡す。

## 受け入れ条件

- `skills/handoff/SKILL.md` が500行未満で、frontmatterに `name` と `description` だけを持つ。
- `agents/openai.yaml` が `$handoff` を含む初期プロンプトを持つ。
- GistのMITライセンスと出典が保存される。
- 既存の70 Skillと新しい `handoff` の計71 Skillが検証を通る。
- READMEの収録数、利用例、ChatGPTでの制限が更新される。
- Draft PRのCIが成功する。
